## Coding Standards (Mahir Style)

### Object-Oriented Design
```typescript
// GOOD: Clear class responsibilities, single purpose
class AuthenticationService {
  // Dependencies injected, not instantiated
  constructor(
    private readonly userRepository: UserRepository,
    private readonly tokenService: TokenService,
    private readonly logger: Logger
  ) {}

  // Methods do one thing well
  async authenticate(credentials: Credentials): Promise<AuthResult> {
    // Implementation follows Command-Query Separation
  }
}

// BAD: God class, mixed responsibilities, procedural style
class UserHandler {
  handleEverything() { /* 500 lines of spaghetti */ }
}
```

### SOLID Principles Applied

**S - Single Responsibility**
```typescript
// Each class has one reason to change
class OrderValidator { /* only validation logic */ }
class OrderPersistence { /* only database operations */ }
class OrderNotifier { /* only notification logic */ }
```

**O - Open/Closed**
```typescript
// Open for extension, closed for modification
interface PaymentProcessor {
  process(payment: Payment): Promise<PaymentResult>;
}

class StripeProcessor implements PaymentProcessor { }
class PayPalProcessor implements PaymentProcessor { }
// Add new processors without modifying existing code
```

**L - Liskov Substitution**
```typescript
// Subtypes must be substitutable for their base types
// If it walks like a duck and quacks like a duck...
```

**I - Interface Segregation**
```typescript
// Many specific interfaces > one general-purpose interface
interface Readable { read(): Data; }
interface Writable { write(data: Data): void; }
// Clients only depend on what they use
```

**D - Dependency Inversion**
```typescript
// Depend on abstractions, not concretions
class OrderService {
  constructor(private readonly repository: OrderRepository) {} // Interface, not implementation
}
```

## Design Patterns Reference

Apply these patterns when appropriate:

| Pattern | Use When |
|---------|----------|
| Factory | Creating objects with complex initialization |
| Strategy | Swappable algorithms at runtime |
| Observer | Event-driven communication between components |
| Repository | Abstracting data access layer |
| Decorator | Adding behavior without modifying existing code |
| Adapter | Integrating incompatible interfaces |
| Command | Encapsulating operations as objects |
| Builder | Constructing complex objects step-by-step |

<example>
**Factory Pattern for Service Creation**
```typescript
// The factory encapsulates the complexity of service instantiation
// so calling code doesn't need to know about dependencies
class ServiceFactory {
  create(type: ServiceType): Service {
    const logger = new Logger(type);
    const config = ConfigLoader.forService(type);
    
    switch (type) {
      case ServiceType.Auth:
        return new AuthService(logger, config, this.tokenService);
      case ServiceType.Payment:
        return new PaymentService(logger, config, this.stripeClient);
      default:
        throw new UnknownServiceError(type);
    }
  }
}
```
</example>

## Error Handling Standards

```typescript
// Always use typed errors with context
class AuthenticationError extends Error {
  constructor(
    message: string,
    public readonly code: AuthErrorCode,
    public readonly userId?: string
  ) {
    super(message);
    this.name = 'AuthenticationError';
  }
}

// Async operations MUST have error handling
async function processPayment(order: Order): Promise<PaymentResult> {
  try {
    const result = await paymentGateway.charge(order.total);
    return { success: true, transactionId: result.id };
  } catch (error) {
    // Log with context for debugging
    logger.error('Payment failed', { orderId: order.id, error });
    
    // Rethrow typed error for caller to handle
    throw new PaymentError('Payment processing failed', error);
  }
}
```

## Anti-Patterns (What You Must Avoid)

1. **God Classes**: No class should exceed ~200 lines or have more than one responsibility
2. **Primitive Obsession**: Use domain types, not raw strings/numbers for business concepts
3. **Feature Envy**: Methods should operate on their own class's data
4. **Shotgun Surgery**: Changes should not require modifications across many files
5. **Magic Numbers**: All constants must be named and documented
6. **Copy-Paste Code**: Extract common logic into shared utilities
